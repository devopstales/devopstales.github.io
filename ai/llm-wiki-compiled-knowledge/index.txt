RAG became the default answer to giving models external knowledge: chunk, embed, retrieve at query time, generate. Useful — and overused. RAG optimizes access, not representation: it finds fragments but builds no stable domain understanding, retrieves context but never decides the canonical explanation. An LLM Wiki moves synthesis to ingest time, compiling sources into structured, linked, human-readable knowledge before any question arrives.

## Query Time vs Ingest Time

```plaintext
  RAG:      query --&gt; retrieve chunks --&gt; assemble --&gt; answer (then forget)
  LLM Wiki: sources --&gt; summarize --&gt; structure --&gt; link --&gt; review --&gt; reuse
```

Per-query synthesis re-derives relationships, resolves contradictions, and rebuilds explanations from scratch — then discards the work. Fine for simple questions over large changing corpora; wasteful when concepts repeat. Ingest-time compilation pays once for coherence: curated stable domains, repeated conceptual questions, human-readable reusable pages.

| Dimension | RAG | LLM Wiki |
|---|---|---|
| Timing | Query time | Ingest time |
| Operation | Retrieve chunks | Compile knowledge |
| Best corpus | Large, changing | Curated, stable |
| Output | Generated answer | Structured pages |
| Infrastructure | Search index / vector DB | Markdown / wiki structure |
| Strength | Flexible access | Reusable synthesis |
| Weakness | Fragmented context | Maintenance drift |

Complementary, not rival: raw documents to source store, wiki synthesis to reviewed pages, search index over both, RAG retrieving raw plus compiled with citations. Representation and retrieval are different layers — the paradigm map lives in [PKM vs RAG vs Wiki vs Memory](/ai/pkm-rag-wiki-memory/).

## How the Pipeline Works

No single implementation, same stages. Collect sources (posts, PDFs, notes, transcripts, READMEs) preserved as their own layer — generated pages are derived interpretation, and every claim must answer &#34;where did this come from?&#34; Ingest by extracting topics, entities, definitions, claims, decisions, contradictions, open questions: reshape conceptually, don&#39;t just chunk for search. Summarize to argument structure — problem, assumptions, tradeoffs, dependencies, uncertainties — not shorter prose. Structure into topic, concept, comparison, glossary, how-to, and [decision record](/ai/decision-records-ai-development/) pages with boundaries and recurring shape; a pile of summaries isn&#39;t a wiki. Link explicitly — concept to concept, tool to comparison, problem to solution, source to derived page — because links build the knowledge graph summaries alone never form. Then review: generated structure creates authority, and authority without human verification embeds hallucinations as ground truth for every future reader and retriever.

## Adjacent Systems, Sharp Edges

Summarization compresses; a wiki adds pages, links, indexes, provenance, revision history, conflict detection — without those it&#39;s a folder of summaries. Knowledge graphs hold explicit machine-queryable relations; wikis hold human-readable explanations — mature systems run both. Agent memory stores behavioral context (preferences, project rules, yesterday&#39;s attempts); wikis store represented knowledge (patterns, comparisons, why-outbox-matters). Mixing them produces unauditable hybrids — memory&#39;s engineering split is covered in [memory systems](/ai/memory-systems-ai-assistants/).

## Where It Wins and Dies

Wins on stable domains, research synthesis (recurring meta-questions over papers and notes), personal knowledge systems, technical blogs with pillar and comparison structure, and small governed team bases (decisions, runbooks, postmortems — with an owner). Dies on fast-moving data (inventory, prices, incidents — retrieve or call APIs instead), unmanaged millions-scale corpora (access control, lineage, dedup, freshness need more than Markdown), low-quality sources (polished pages over contradictions manufacture false confidence), and absent review (one bad generated page poisons many future queries, unlike one bad RAG answer).

Failure quartet: maintenance drift (pages detaching from sources — the central ops risk), ingest-time hallucination (wrong synthesis baked in, amplified by later retrieval), over-structuring (empty taxonomies, duplicate concepts, fake completeness — measure reuse, not page count), unclear ownership (who reviews, approves, deletes, resolves, canonicalizes — without it, another abandoned wiki).

## Four Deployment Shapes

Personal (notes to reviewed Markdown in Obsidian or a static site — researchers, engineers, bloggers), team (ingest workflow, draft pages, mandatory review queue, published wiki plus search/RAG — never publish generated drafts straight to shared truth), wiki-plus-RAG (raw and compiled both indexed, answers cited — the balanced production shape), site architecture (pillar pages, topic maps, comparisons, internal links turning a blog into a navigable knowledge system for humans and machines).

## Design Rules

Raw sources separate from derived pages. Markdown everywhere — portable, diffable, versionable, boring enough to outlive platforms. Provenance on every page: sources, generation and review dates, changes, approver. Fewer better pages: twenty maintained beats two hundred generated. Meaningful link types (contrasts with, depends on, expands on) over random connections. Uncertainty marked openly — confirmed, likely, disputed, outdated, needs review — protecting readers from false confidence and flagging maintenance targets. Evaluate on reuse, findability, contradiction visibility, accuracy, staleness detection, synthesis savings, and RAG quality lift — decoration scores zero on most of these.

## Summary

Summarize, structure, link, review, reuse — at ingest time, not query time. For stable curated knowledge that humans and agents revisit, compilation beats retrieval; for everything fast-moving, retrieval still wins. Know which layer you&#39;re building.
